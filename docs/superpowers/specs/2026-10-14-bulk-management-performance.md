# 批量管理与后台响应优化

用户要求文章后台支持批量删除，并优化同步、修改与发布的整体响应。沿用现有内容工作台和 GitHub／Cloudflare 部署架构。

## 操作设计

文章与草稿按各自版本选择，媒体按文件选择。提供勾选、全选当前筛选结果、取消选择和批量删除；更换筛选条件时清空选择，避免误操作隐藏内容。确认对话框展示数量和内容名称。一次最多处理 100 项。

已发表内容集中生成一个删除变更，列表立即显示“待删除”，经过原有检查与合并后正式移除。独立草稿撤回其待处理 PR，保留已发表版本；GitHub 中可重新打开该 PR 恢复。批量媒体删除沿用引用保护，提交前统一验证所有选择。网络导致部分成功时返回已完成和失败项，只保留失败项以便重试。

## 性能设计

主要瓶颈是每次操作重复读取仓库权限、分支、提交、目录、全部 PR 和内容，保存后又完整刷新。同步仍读取最新分支与 PR 版本，只缓存按 SHA 固定的提交、目录和文件内容。相同版本的 PR 文件差异可复用；缓存有容量上限，退出登录清空。

保存、删除和上传直接返回经过确认的新工作区状态，页面无需再完整同步。写入时并行读取新目录和创建提交，复用已提交的文本；新分支使用唯一后缀，省去探测名称的请求。批量文件通过一个 Git tree 和 commit 修改，不逐条调用单项删除。

发布并行核对文件与检查状态，始终使用确切提交 SHA 合并，保持分支保护和图片引用检查。页面即时显示当前阶段，阻止重复操作。内容提交完成与 Cloudflare 构建完成分别提示。

## 验证

测试未改变版本的同步请求预算、并发同步合并、保存结果完整性、批量删除的一次提交、全部预验证、部分失败、版本冲突、图片引用与发布范围。保留现有测试；运行类型检查和生产构建。在临时内容目录验证实际批量操作，再核验生产界面与 GitHub 登录。
